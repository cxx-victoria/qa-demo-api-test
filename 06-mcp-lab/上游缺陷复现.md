## 复现报告 1：CLI 的流式路径因未捕获 EPIPE 而崩溃

* **上游 issue**：<https://github.com/modelcontextprotocol/inspector/issues/2412>
  「CLI's long-lived stream path can crash with an uncaught EPIPE」
* **上游状态**：open，label `bug`
* **涉及代码**：`clients/cli/src/handlers/consume-outcome.ts`（代码内自带 `TODO(#1432)`，
  承认流式路径尚未处理 EPIPE / stdout 错误）
* **被测版本**：2.7.0
* **操作系统**：Windows 11（build 26200）
* **前置条件**：Node.js v22.23.2；被测 Server 单次响应超过 Windows 管道缓冲区（64 KB）
* **issue 原文的关键限制**：作者写明「I have not run `mcp-inspector --cli … | head -n 5` live
  to observe the crash」——**只做了静态代码审查，没有实跑**

### 复现步骤

1. 准备一个能返回超大响应的 MCP Server（本目录 `big_server.py`，工具 `blob(size_kb)`）
2. 用 Inspector CLI 调用它，输出交给一个"读到第一块数据就退出"的下游
   （等价于 issue 里说的 `| head` / `| grep -m1` / `| less`，都会提前关闭管道）
3. 观察 CLI 进程的退出码与 stderr

```powershell
cd D:\qa-projects\06-mcp-lab\upstream-repro
.\.venv\Scripts\Activate.ps1        # 或用 D:\qa-projects\06-mcp-lab\.venv

node repro_driver.js                 # 512 KB 响应
$env:REPRO_SIZE_KB="8"; node repro_driver.js   # 对照组：8 KB 响应
```

### 实际结果（**复现成功**）

```
被测响应大小      : 512 KB
退出码            : 1
关闭前读到字节数  : 65536
stderr 是否含 EPIPE: 是 → 复现成功

node:events:497
      throw er; // Unhandled 'error' event
      ^
Error: EPIPE: broken pipe, write
    at Socket._write (node:internal/net:63:18)
    at Writable.write (node:internal/streams/writable:510:10)
    at file:///…/@modelcontextprotocol/inspector/clients/cli/build/index.js:13:20
    at awaitableLog (…clients/cli/build/index.js:12:10)
    at emitResult (…clients/cli/build/index.js:15346:11)
    at consumeMethodOutcome (…clients/cli/build/index.js:15373:11)
    at callMethod (…clients/cli/build/index.js:17898:11) {
  errno: -4047, syscall: 'write', code: 'EPIPE'
}
Node.js v22.23.2
```

调用栈直接落在 `consume-outcome` 与 `awaitableLog` 上，与 issue 指向的 `consume-outcome.ts` 一致。

### 我补充的关键信息（issue 原文没有的部分）

**1）精确定位了触发条件 —— 响应体必须超过管道缓冲区（64 KB）。** 做了对照实验：

| 响应大小 | 关闭前读到字节 | 退出码 | 结果 |
|---------|---------------|--------|------|
| 8 KB | 16485 | 0 | 正常退出 |
| 32 KB | 65536 | 0 | 正常退出 |
| 62 KB | 65536 | 0 | 正常退出 |
| **64 KB** | 65536 | **1** | **EPIPE 崩溃** |
| 100 KB | 65536 | 1 | EPIPE 崩溃 |
| 512 KB | 65536 | 1 | EPIPE 崩溃 |

> 这说明：**只有单次输出超过 64 KB（Windows 管道缓冲区）时才会触发**。
> 输出小于缓冲区时，写入一次性完成、进程随即正常退出，因此不会命中该缺陷。
> 这也解释了为什么平时用 `| head` 看小响应根本发现不了问题 —— 它是个"大响应才炸"的偶发问题。

**2）确认崩溃方式是 Node 的未处理 error 事件**，即 `process.stdout` 的写入错误没有被捕获，
进程以退出码 1 终止并打印整段调用栈，而不是像 `SIGPIPE` 那样安静退出。

### 影响

* CI 中把 CLI 输出接到 `head`、`grep -m1`、日志截断工具时，会出现**随机构建失败**
* 退出码 1 会被 CI 判为失败，但真实原因（下游提前退出）与被测 MCP Server 毫无关系，**极易误判**
* 用户的日常习惯（`| head` 看前几行）就会踩到，属于高频路径

### 建议修复

在 `awaitableLog` / `emitResult` 的 stdout 写入处捕获 `EPIPE`：
捕获到 `EPIPE` 时按"下游已关闭"正常退出（退出码 0），不打印调用栈；
其余写入错误仍按真实错误处理。这与代码里已有的 `TODO(#1432)` 是同一处。

## 复现报告 2：CLI 宣称自己支持 MCP Apps，但它渲染不了

* **上游 issue**：<https://github.com/modelcontextprotocol/inspector/issues/2403>
  「CLI and TUI advertise `io.modelcontextprotocol/ui` although they cannot render MCP Apps」
* **上游状态**：open，label `bug` `v2`
* **涉及代码**：`core/mcp/extensions.ts`（默认注册 MCP Apps 扩展）+
  `InspectorClient`（各客户端未覆盖该默认值）
* **被测版本**：2.7.0　｜　客户端：`inspector-cli`

### 复现思路

这个缺陷不是"崩溃"，而是**客户端说错话**，所以要用"抓包"的方式验证：
让 CLI 连一个只负责记录报文的 Server（本目录 `spy_server.py`），
把它发出去的 `initialize` 请求原样存下来，然后检查 `capabilities` 里到底声明了什么。

### 复现步骤

```powershell
cd D:\qa-projects\06-mcp-lab\upstream-repro
.\.venv\Scripts\Activate.ps1

npx -y @modelcontextprotocol/inspector --cli python spy_server.py --method tools/list --format json

# 查看抓到的客户端报文
Get-Content client_requests.jsonl -Encoding UTF8
```

### 实际结果（**复现成功**）

抓包文件 `client_requests.jsonl` 第一行，就是 CLI 发来的 `initialize` 请求：

```json
{"method": "initialize", "params": {"protocolVersion": "2025-11-25",
 "capabilities": {
   "roots": {"listChanged": true},
   "extensions": {
     "io.modelcontextprotocol/tasks": {},
     "io.modelcontextprotocol/ui": {"mimeTypes": ["text/html;profile=mcp-app"]},
     "io.modelcontextprotocol/skills": {}
   }
 },
 "clientInfo": {"name": "inspector-cli", "version": "2.7.0"}, "jsonrpc": "2.0", "id": 0}
```

**关键点**：`clientInfo.name` 确实是 `inspector-cli`，而它的 `capabilities.extensions`
里**明确包含了 `io.modelcontextprotocol/ui`，还带上了 `text/html;profile=mcp-app` 的 mimeTypes**
—— 声明"我能渲染 MCP App"。

但 CLI 只有 `--app-info` 这个元数据探测开关，**根本不渲染任何 UI**。issue 的描述被实测证实。

### 我补充的关键信息

报文字段是**原始 JSON**（不是转述），可直接作为证据；
同时记录到 protocolVersion 协商结果为 `2025-11-25`，
以及除 `ui` 之外还声明了 `io.modelcontextprotocol/tasks` 与 `io.modelcontextprotocol/skills`
—— 说明这是**默认能力的批量注册问题**，不只是 `ui` 一项，修复时应统一审视。

### 影响

被测 Server 会**根据客户端的扩展声明**决定要不要返回 UI 资源。
于是 Server 对着 CLI 返回了 UI，而 CLI 消费不了 ——
**测试工具自身对被测系统撒谎，导致测试结论失真**。对以"协议一致性"为目的的工具来说，这是原则性问题。

### 建议修复

只有真正能渲染 MCP Apps 的客户端（Web）才默认声明 `io.modelcontextprotocol/ui`；
CLI / TUI 默认不声明，若确有探测需求，通过显式开关（如 `--app-info`）按需开启。

## 复现报告 3：Windows 路径分隔符 —— **尝试复现，未发现问题**

* **上游 issue**：<https://github.com/modelcontextprotocol/inspector/issues/2416>
  「No visible test for Windows path separators in launcher/CLI argument forwarding」
* **上游状态**：open，label `bug`　｜　被测版本：2.7.0
* **issue 原文的关键限制**：「I have not run this on a Windows machine to observe an actual failure」

### 复现步骤

在 Windows 上用**反斜杠绝对路径**和**含空格的路径**作为被转发的 Server 命令：

```powershell
cd D:\qa-projects\06-mcp-lab
.\.venv\Scripts\Activate.ps1

# ① 反斜杠绝对路径作为被转发的 Server 命令
npx -y @modelcontextprotocol/inspector --cli `
  "D:\qa-projects\06-mcp-lab\.venv\Scripts\python.exe" `
  "D:\qa-projects\06-mcp-lab\server.py" `
  --method tools/list --format json

# ② 含空格的路径：先造一个带空格的目录，再把它当参数传进去
New-Item -ItemType Directory -Force -Path "D:\qa-projects\06-mcp-lab\path with space" | Out-Null
Copy-Item "D:\qa-projects\06-mcp-lab\server.py" "D:\qa-projects\06-mcp-lab\path with space\server.py" -Force
npx -y @modelcontextprotocol/inspector --cli python "path with space\server.py" --method tools/list --format json

# ③ --cwd 指向含空格的目录
npx -y @modelcontextprotocol/inspector --cli python server.py --cwd "path with space" --method tools/list --format json
```

> 三条都应返回 `{"result":{"tools":[ … ]}}`，退出码 0。

### 实际结果（**未复现出故障**）

| 场景 | 退出码 | 结果 |
|------|--------|------|
| 反斜杠绝对路径作为转发命令 | 0 | 正常返回 3 个工具的 schema |
| 含空格的相对路径作为参数 | 0 | 正常返回 3 个工具的 schema |
| `--cwd` 指向含空格目录 | 0 | 正常返回 3 个工具的 schema |

### 结论（这才是测试该给出的判断）

**运行期没有缺陷，缺的是测试覆盖。** 这个 issue 描述的是"没有任何测试覆盖 Windows 路径分隔符"，
而不是"Windows 上会失败"。实测证明：**当前版本在 Windows 上转发反斜杠与含空格路径都正常工作**。

所以正确的处理不是"修 bug"，而是**补一条回归测试**把现在正确的行为钉住，
防止将来重构时退化。这与我在自己项目里做的事完全一样 ——
「缺陷」和「测试盲区」是两类问题，测试报告里必须分清。

> 简历上这样写才专业：
> 复现 2 个上游缺陷并补充运行期证据；对第 3 个候选 issue 完成反向验证，
> 判定其为**测试覆盖缺口而非运行时缺陷**，避免误导维护者。

## 附一：同步给上游的技巧

可以直接在对应 issue 下留言补充证据（**不需要写代码也算贡献**）。模板：

```markdown
Verified on Windows 11 (build 26200), inspector 2.7.0, Node v22.23.2.

Reproduced with a server whose single response exceeds 64 KB, piped into a reader
that exits after the first chunk (equivalent to `| head`):

    exit code 1
    Error: EPIPE: broken pipe, write
      at awaitableLog (clients/cli/build/index.js:12:10)
      at emitResult (clients/cli/build/index.js:15346:11)
      at consumeMethodOutcome (clients/cli/build/index.js:15373:11)

Control experiment — the crash does not occur below the pipe buffer size:

    8 KB / 32 KB / 62 KB → exit 0
    64 KB / 100 KB / 512 KB → exit 1 (EPIPE)

So the precondition is: stdout for a single call exceeds the 64 KB OS pipe buffer
AND the downstream reader closes early.
```
