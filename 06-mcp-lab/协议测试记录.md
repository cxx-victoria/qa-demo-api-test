## 三、缺陷详情

### MCP-001　`add_task` 未校验空标题（中等）

* **复现步骤**：调用 `add_task`，`title` 传空字符串（或纯空格）
* **期望结果**：返回参数校验错误，不创建任务
* **实际结果**：创建成功，返回 `created: 9dced633`，列表里出现一条空标题任务
* **影响**：脏数据入库。下游展示会出现空白条目，用户无法辨认也无法定位删除
* **建议修复**：入口处校验 `title.strip()` 非空；用 `raise ToolError("title 不能为空")` 让客户端拿到可读错误

### MCP-002　`add_task` 未限制标题长度（中等）

* **复现步骤**：调用 `add_task`，`title` 传 10000 个字符
* **期望结果**：拒绝或截断
* **实际结果**：创建成功，整串写入数据库
* **影响**：单条记录可被撑到任意大小，可能拖慢列表查询、撑爆下游 UI，属于典型的**无上限输入**风险
* **建议修复**：设定长度上限（本修复取 200 字符），超长时返回明确错误

### MCP-003　`delete_task` 删除不存在的 id 仍返回成功（严重）

* **复现步骤**：调用 `delete_task`，`task_id="not-exist-id"`（该 id 根本不存在）
* **期望结果**：返回"未找到"
* **实际结果**：返回 `deleted`，`isError=false`
* **影响**：**这是最危险的一条**。调用方（AI Agent 或上游系统）会把"已经删掉了"当成事实，
  于是可以复现经典问题：批量删除任务时部分 id 写错，程序依然全报成功，
  实际有数据没删掉却没人知道；反过来也可能让调用方跳过重试或补偿逻辑
* **根因**：`DELETE FROM tasks WHERE id = ?` 对 0 行受影响的情况没有判断
* **建议修复**：检查 `cursor.rowcount`，为 0 时返回未找到

### MCP-004　`delete_task` 传空 id 仍返回成功（中等）

* **复现步骤**：调用 `delete_task`，`task_id=""`
* **期望结果**：明确报错
* **实际结果**：返回 `deleted`
* **影响**：与 MCP-003 同源。空参数通常是上游拼接失败或模型漏填参数，
  此时仍回"成功"会把真实的调用错误掩盖掉
* **建议修复**：先校验 `task_id` 非空

### MCP-005　`list_tasks` 返回的不是合法 JSON（低）

* **复现步骤**：调用 `list_tasks`，观察返回文本
* **期望结果**：返回合法 JSON 数组，下游可直接解析
* **实际结果**：返回 Python repr —— `[{'id': 'dd232c82', 'title': '正常任务', 'done': False}]`
  （单引号、`True/False`、中文不转义），`json.loads()` 解析会抛异常
* **影响**：跨语言调用必然踩坑。Python 侧用 `eval`/`ast.literal_eval` 勉强能读，
  但 JS / Go / Java 客户端拿到的就是一串无法解析的文本
* **建议修复**：`return json.dumps(items, ensure_ascii=False)`

> 同一份用例文件既能当缺陷清单，又能当回归验证，不用维护两套脚本。

## 五、未覆盖项说明（用例 21 / 24）

测试报告写"全部通过"是不专业的，**主动说明哪些没覆盖、为什么**才是。

| 用例 | 未覆盖原因 | 后续怎么补 |
|------|-----------|-----------|
| 21 超时 | 本 Server 没有耗时工具，客户端无法感知超时 | 增加一个 `sleep(seconds)` 工具，再用 `--connect-timeout` 或客户端超时参数触发 |
| 24 内存泄漏 | 需要外部工具持续采样进程内存（如 Windows 性能计数器 / `tracemalloc`） | 用 `tracemalloc` 在循环调用前后打快照，比较对象增量 |

此外还有两个**已知的测试盲区**，如实记录：

1. **真实并发未覆盖**。stdio 传输是单连接串行，用例 19 只是"快速连续调用"，
   不等于并发。真正的并发要换 HTTP/SSE 传输后再压测。
2. **stdio 下服务端日志不可见**。协议占用了 stdout，`print()` 会破坏协议，
   所以调试信息只能写 stderr 或文件 —— 这也是排查 MCP 问题最容易踩的坑。
