# Fiddler Classic 抓包分析

> 用 **Fiddler Classic** 对 `QA Demo API` 做的一次抓包分析。
> 目的有两个：
> ① **独立验证** Postman 阶段发现的缺陷（双工具交叉验证）；
> ② 演示"**中间人可以在传输途中改包**"，并把它做成**可量化的证据**。

---

## 0. 环境与工具

| 项目 | 内容 |
|------|------|
| 被测系统 | QA Demo API（FastAPI + SQLite），`http://localhost:8000` |
| 抓包工具 | Fiddler Classic 5.x（免费版，非商业用途） |
| 抓包方式 | 显式代理（PowerShell `-Proxy http://127.0.0.1:8888`）+ Fiddler 专用域名 `localhost.fiddler` |
| HTTPS 解密 | **未启用**（本次只测明文 HTTP，无需装证书） |
| 会话存档 | `business-flow.saz`（162 个会话） |
| 辅助工具 | Postman（同一批接口的第二套证据） |
| 测试日期 | 2026-09-27 |

## 2. 关键发现

### 2.1 鉴权靠 `Authorization` 请求头传递

抓到 `POST /tasks` 的完整请求头：

```
POST /tasks HTTP/1.1
User-Agent: Mozilla/5.0 (Windows NT; Windows NT 10.0; zh-CN) WindowsPowerShell/5.1.26100.9444
Content-Length: 36
Content-Type: application/json
Authorization: Bearer fb7bf2c8bc1a448d9c92055a39c30f3d
Host: localhost:8000
```

**结论**

* 这是一套 **Bearer Token 放在请求头** 的鉴权方式，不属于 Cookie/Session 体系；
* token 是 32 位十六进制字符串，由 `POST /login` 下发；
* 抓包可以直接看到明文 token —— **在 HTTP 下凭证是完全暴露的**。

**证据**：`02-Fiddler里的Authorization头.png`

> ⚠️ 上面的 token 是本地演示环境的值，服务重启即失效。

---

### 2.2 【缺陷 D3】未授权删除 —— 抓包侧的交叉验证（高危）

**事实链**

1. `POST /tasks` 创建一条任务，服务端返回
   `{"id":"97c4c371975b4424b80279418275b00e","title":"Fiddler????","done":0}`
2. 随后发出 `DELETE /tasks/97c4c371975b4424b80279418275b00e`，
   **该请求完全没有携带 `Authorization` 请求头**（构造脚本里就没有这个头）
3. 抓包结果显示：状态码 **204**，响应体 **0 字节**（即"删除成功"）
4. 之后重新查询：该 id **已不在数据库里**（本次复查确认：`97c4c371…` 已查不到）

**期望**：无凭证调用 `DELETE` 应返回 **401 / 403**

**实际**：**204 删除成功**

**与 Postman 阶段的一致性**

Postman 阶段用"把 `Authorization` 行取消勾选"的方式做过同样的实验，
同样得到 204 且数据消失。**两个独立工具、两种独立方法，结论一致**：

> `DELETE /tasks/{id}` 服务端**根本没有做身份校验**，
> 任何匿名请求只要拿到 id 就能删除数据。
> 由于 `GET /tasks` 也不鉴权，攻击者可以**先列全部 id，再逐个删光**。

**证据**：`01-Fiddler抓到完整业务流.png`（第 15 行 204）、
Postman 侧 `02-无鉴权删除204.png`

---

### 2.3 【响应篡改】纯 HTTP 下响应可被任意修改（本次最硬的一条证据）

**目的**：证明"抓包工具不只是能看，还能**在传输途中改**"，
而且客户端**完全无法察觉**。

**操作**

1. 在 Fiddler 的 QuickExec 里执行 `bpafter /tasks`，给 `/tasks` 的**响应**设断点
2. 客户端发一次 `GET /tasks`
3. 响应被 Fiddler **拦下**，在下半部分（Response）的 **`TextView`** 里，
   把列表中最后一条的 `"done": false` 改成 **`"done": true`**
   （Fiddler 状态栏留下记录：`Auto-saved changes to response from Standard.ResponseTextViewer at 19:49:28`）
4. 点 **`Run to Completion`** 放行

**结果对比（三方数据）**

| 数据来源 | 那条记录（id `9616438d002e48e7a1f60bfa203e32e1`）的 `done` |
|---------|------------------------------------------------------|
| **服务端数据库真实值** | **`false`** |
| Fiddler 抓到的响应体 | **`true`**（被改过） |
| 客户端最终收到的数据 | **`true`**（PowerShell 打印：`done : True`） |

> ✅ **这就是铁证**：数据库里明明是 `false`，
> 客户端却收到了 `true`，用户界面上看到的状态是**假的**。

**影响**

* 任何能接触网络链路的中间人（同一 WiFi、代理、运营商、恶意网关）
  都可以**单向篡改**业务数据，客户端没有任何感知；
* 对"任务完成状态""订单金额""审批结果""余额"这类字段来说，这是**业务级风险**，
  而不只是技术问题。

**修复建议**

1. 全站强制 **HTTPS**（TLS 保证传输完整性）；
2. 客户端开启 **证书校验**，关键 App 建议 **证书固定（Certificate Pinning）**；
3. 关键字段加**服务端签名/校验和**，让篡改可被发现。

**证据**：`05-修改响应内容后的界面（false 改成 true）.png`、
`06-截图（PowerShell 客户端最终结果）.png`

### 2.4 【缺陷 D1】未文档化的长度限制 —— 用断点改包复现

**操作**

1. QuickExec 执行 `bpu /tasks`（对 `/tasks` 的**请求**设断点）
2. 客户端发 `POST /tasks`
3. 请求被拦下后，在 **`TextView`** 里把 `title` 改成 **101 个字符**
4. `Run to Completion` 放行

**结果**：服务端返回 **422**，`{"detail":"title 过长"}`

**与 Postman 阶段一致**：Postman 直接发 101 字符也是 422，
100 字符则 201。**限制确实卡在 100**，但接口文档里没有任何长度说明。

> 💡 这一条同时展示了另一层价值：
> **"用断点改包"可以在不改动任何代码、不重发请求的前提下，
> 现场构造出边界用例** —— 这是纯 UI 工具（Postman）做不到的。

**证据**：`03-断点改包-请求被拦下.png`

---

### 2.5 附带发现：中文在传输前被替换成了 `????`

创建任务时用了中文标题，Fiddler 抓到的请求体是：

```
{"title":"Fiddler????","done":false}     (Content-Length: 36)
```

四个中文字符变成了 **4 个 `?`**，而且 `Content-Length` 只有 36 字节
→ **中文字符在进入 HTTP 请求之前就已经丢掉了**，
是**发送端（PowerShell 参数编码）**的问题，**不是服务端的缺陷**。

**要区分两种"乱码"**（这个区分很能体现排查能力）：

| 现象 | 本质 | 归属 |
|------|------|------|
| 请求体里出现 `????`，数据库里存的也是问号 | **数据真的丢了** | 客户端编码问题（请求侧） |
| PowerShell 控制台里"压测任务"显示成 `å...` | **数据没坏**，只是终端用错了代码页渲染 | 显示问题（终端侧） |

> 我通过接口复查确认：数据库里那批任务的标题**确实是正确的"压测任务"**，
> 只是 PowerShell 控制台显示乱码 → 属于第 2 种，**数据完好**。

## 3. 工具使用复盘（踩坑与解决）

| 坑 | 现象 | 解决办法 |
|----|------|---------|
| **Fiddler 默认抓不到 localhost** | 列表里完全没有自己的请求 | 用显式代理 `-Proxy http://127.0.0.1:8888`；或访问 `http://localhost.fiddler:8000/...` |
| **`JSON` 检查器是只读的** | 想改响应却改不动 | 改内容必须切到 **`TextView`** 或 **`Raw`** 标签 |
| **断点忘记清除** | 之后每个请求都被卡住 | QuickExec 里 `bpu` / `bpafter` **不带参数**即清除 |
| **Fiddler 接管系统代理** | 关掉后浏览器上不了网 | 用 `File → Exit` 正常退出，让 Fiddler 还原系统代理 |
| **一堆 `Tunnel to …:443`** | 列表很乱 | 属正常现象（未解密 HTTPS）；用 `cls` 清空列表后再抓自己的请求 |

## 4. 双工具交叉验证矩阵

同一批缺陷，用两套完全独立的工具验证：

| 验证点 | Postman 侧证据 | Fiddler 侧证据 | 是否一致 |
|--------|---------------|---------------|---------|
| 业务流 200 / 201 / 200 / 204 | `01`~`04` 截图 | `01-Fiddler抓到完整业务流.png` | ✅ |
| 鉴权头 `Authorization: Bearer …` | `01-Authorization请求头.png` | `02-Fiddler里的Authorization头.png` | ✅ |
| **无鉴权删除返回 204 且数据消失** | `02`、`03` | `01` 第 15 行 + 复查 | ✅ |
| **title 101 字符被拒 422（限 100）** | `05`、`06` | `03-断点改包-请求被拦下.png` | ✅ |
| 不存在的 id 返回 500 | `04-不存在的id返回500.png` | —（未在 Fiddler 侧复测） | — |
| 响应可被中途篡改 | —（Postman 不做这类事） | `05`、`06` 截图 + 数据库比对 | ✅ **Fiddler 独有** |

**这套矩阵的意义**：
"同一个缺陷只有一个工具能复现"容易被认为是环境巧合；
**两个不同原理的工具给出同一结论**，才能说明它是**系统本身的问题**。

---

## 5. 结论

1. 本次抓包覆盖了一次完整业务流（登录 → 创建 → 查询 → 删除），
   并成功演示了**请求改包**与**响应篡改**两种中间人手法。
2. 抓包结果**独立复现**了 Postman 阶段的两条缺陷：
   **未授权删除（D3，高危）** 与 **未文档化的长度限制（D1）**。
3. 新增一条 Postman 无法覆盖的结论：
   **纯 HTTP 下响应可被任意篡改**（数据库 `false` → 客户端 `true`），
   这是一条**业务级安全风险**。
4. 排查过程中还区分开了两类容易混淆的问题：
   **客户端编码丢失（请求体出现 `????`）** 与
   **终端显示乱码（数据其实完好）** —— 前者是环境问题，后者是显示问题，
   **都不是服务端缺陷**。
