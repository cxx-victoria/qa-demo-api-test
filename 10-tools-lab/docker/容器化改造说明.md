# 容器化与数据库迁移改造说明

> **改造对象**：`00-demo-api`（自研 FastAPI 客服系统）
> **改造内容**：本地进程 + SQLite → **Docker 容器 + MySQL 8**
> **改造日期**：2026-10-03
> **配套证据**：本目录下 4 张截图 + 下方第 7 节的实测数据

---

## 1. 改造目标

| 目标 | 验收标准 |
|------|---------|
| 服务可容器化运行 | `docker compose up -d` 一条命令拉起全部依赖 |
| 数据库从 SQLite 迁移到 MySQL | 接口行为不变，数据落在 MySQL |
| **不改动接口契约** | 原有 **39 条接口用例零改动全部通过** |
| 数据一致性用例可跨数据库运行 | 15 条 API↔DB 交叉校验用例在 MySQL 上通过 |
| 测试不污染数据 | 测试侧用**只读账号**连接 |

## 4. 四个关键设计

### 4.1 Dockerfile 分层构建

```dockerfile
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt -i <国内源>
COPY app.py db.py ./
```

**先拷依赖、后拷代码**：改业务代码不会触发重新装依赖，**构建从分钟级降到秒级**。
配合 `.dockerignore` 排除 `.venv/`（否则构建上下文会带上几百 MB）。

### 4.2 健康检查 + 启动顺序

```yaml
  api:
    depends_on:
      mysql:
        condition: service_healthy      # 不是"容器起来了"，而是"MySQL 真能接受连接"
  mysql:
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "127.0.0.1", "-uroot", "-proot123456"]
      interval: 5s
      retries: 30
```

**为什么重要**：MySQL 从容器启动到能接受连接有十几秒空窗。如果只写 `depends_on: [mysql]`，
API 会在数据库还没就绪时启动，**连接失败退出**。

> 这跟 CI 里"**服务未就绪导致误报**"是同一类问题，这里是容器编排层面的解法。

### 4.3 数据卷持久化

```yaml
    volumes:
      - mysql-data:/var/lib/mysql
```

容器删了数据还在；`docker compose down`（不加 `-v`）不会删数据卷。

### 4.4 测试用只读账号（权限层面保证不污染）

```sql
CREATE USER IF NOT EXISTS 'qa_ro'@'%' IDENTIFIED BY 'qa_ro_pwd';
GRANT SELECT ON qa_demo.tasks TO 'qa_ro'@'%';
```

测试连接时使用 `qa_ro`，**等价于原 SQLite 的 `mode=ro`** ——
把"测试不写坏数据"从**口头约定**变成**数据库权限控制**。

### 4.5 数据库适配层（单点封装的价值）

原代码把数据库访问收敛在一个 `db()` 函数里，因此本次迁移**只改了连接方式**：

```python
class _Conn:
    """把 pymysql 连接包装成 sqlite3 的用法，业务代码不用改。"""
    def execute(self, sql, params=None):
        cur = self._raw.cursor()
        cur.execute(sql.replace("?", "%s"), params or ())   # 占位符转换
        return cur
    def __exit__(self, *exc):
        # 成功 commit / 失败 rollback，并关闭连接
```

* 用 `DB_BACKEND` 环境变量切换 `sqlite` / `mysql`；
* `?` 占位符自动转 `%s`，业务 SQL 一处没改；
* 顺手修掉了原来「`with db() as conn` 只提交事务、不关闭连接」的**连接泄漏隐患**。

## 5. 迁移踩坑清单（**迁移不只是换个连接串**）

| # | SQLite 特有 | MySQL 对应做法 | 影响范围 |
|---|------------|---------------|---------|
| 1 | `ORDER BY rowid` | `ORDER BY id`（或 `created_at, id`） | **实现层 + 测试层各一处** |
| 2 | `typeof(col)` 取字段类型 | 改用 **Python 侧 `type()` 判断** | 测试层 |
| 3 | `file:...?mode=ro` 只读连接 | **只读账号** `qa_ro` | 测试层 |
| 4 | `TEXT PRIMARY KEY` / `INTEGER` | `VARCHAR(32)` / `TINYINT(1)` + `created_at` | 建表语句 |
| 5 | `?` 占位符 | `%s`（由适配层自动转换） | 已在 `db.py` 抹平 |

补充两个实际踩到的坑：

* **`ORDER BY rowid` 只改实现不改测试会得到假失败** ——
  `test_api_list_matches_db_rows` 断言"接口列表与数据库逐条一致（含顺序）"，
  两边排序键必须一致，否则报的是"口径不一致"，**看起来像数据 bug，其实是测试没跟上**。
* **`typeof()` 在 MySQL 里被当成存储过程调用** —— 报
  `execute command denied to user 'qa_ro' for routine 'qa_demo.typeof'`，
  一开始很像权限问题，根因其实是**函数不存在**。

## 6. 对照实验：为什么测试必须与服务"同源"

改造过程中刻意做了四组对照，证明 **"测试读的库" 必须等于 "服务写的库"**：

| 服务后端 | 测试后端 | 结果 | 现象 |
|---------|---------|------|------|
| SQLite | SQLite | ✅ **15 passed** | 同源，全部通过 |
| SQLite | **MySQL** | ❌ 8 failed | 接口返回 1935 条，数据库 0 条 |
| **MySQL** | SQLite | ❌ 8 failed | 接口返回 0 条，数据库 1935 条 |
| **MySQL** | **MySQL** | ✅ **14 passed, 1 skipped** | 同源，通过 |

**结论**：跨层校验类测试（接口 ↔ 数据库）的**第一步永远是证明两边看的是同一份数据**。
本项目的 `test_test_db_is_same_file_service_writes`（"同源自检"）就是为此设计的 ——
在上表第 2、3 行的情况下它**主动报警**，避免了把"环境不一致"误判成"数据一致性缺陷"。

> 该用例在 MySQL 模式下**主动跳过**（`skipif`）：MySQL 下服务与测试连的是同一个库，
> 不存在"两个文件"的场景，因此保留跳过是**有意为之**，不是未覆盖。

## 8. 常用命令速查

```powershell
# 启动 / 重建（改代码后要加 --build，否则容器还是旧镜像）
cd D:\qa-projects\00-demo-api
docker compose up -d --build

# 看状态 / 看日志
docker compose ps
docker logs -f qa-api
docker logs --tail 30 qa-mysql

# 进容器（Linux 环境练习点）
docker exec -it qa-api bash
docker exec -it qa-mysql mysql -uroot -proot123456 -e "use qa_demo; select count(*) from tasks;"

# 停止（不删数据卷）/ 彻底清理（删卷，数据会丢）
docker compose down
docker compose down -v
```

> ⚠️ **两个易踩点**
> 1. `docker compose` 必须在**有 `docker-compose.yml` 的目录**执行，否则报 `no configuration file provided`；
> 2. 第一次启动失败后，**必须删数据卷再重建** —— MySQL 官方镜像的规则是
>    "**数据目录非空就跳过 `/docker-entrypoint-initdb.d` 初始化脚本**"，
>    不删卷的话改了 SQL 也不会生效。
