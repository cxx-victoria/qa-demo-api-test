# Navicat 数据库核查手册（零基础 · 点哪一下都写清楚）

> **本次目标**：用数据库工具直接打开被测系统的 SQLite 文件，
> 做**数据质量核查**，并给接口测试发现的缺陷补上**数据库层的证据**。
>
> 这一步的价值：接口测试只能证明"接口返回了什么"，
> **数据库才能证明"数据到底有没有真的变"**。

4. 结果出现在下半部分网格里

### 6 条核查 SQL 与**实测期望结果**

下面"实测值"是我在你这套环境上刚跑出来的真实数字，
**你跑出来应该基本一致**（总数会随测试数据增加而变化，看数量级即可）。

| # | 检查什么 | SQL | 实测值 | 含义 |
|---|---------|-----|-------|------|
| 1 | 总行数 | `SELECT COUNT(*) FROM tasks;` | **1831** | 基线数字 |
| 2 | 空标题 / 纯空格标题 | `SELECT COUNT(*) FROM tasks WHERE title IS NULL OR TRIM(title) = '';` | **2** | ⚠️ **脏数据**（见 5.3） |
| 3 | 超长标题（>100 字符） | `SELECT COUNT(*) FROM tasks WHERE LENGTH(title) > 100;` | **0** | 接口把超长的挡在门外了 |
| 4 | `done` 出现异常值 | `SELECT COUNT(*) FROM tasks WHERE done NOT IN (0,1);` | **0** | 取值只有 0/1，正常 |
| 5 | 主键是否重复 | `SELECT id, COUNT(*) c FROM tasks GROUP BY id HAVING COUNT(*) > 1;` | **0 行** | 主键唯一性正常 |
| 6 | `done` 分布 | `SELECT done, COUNT(*) FROM tasks GROUP BY done;` | `0 → 1829`、`1 → 2` | 大部分任务未完成 |

再加两条有用的：

| # | 检查什么 | SQL | 实测值 |
|---|---------|-----|-------|
| 7 | 最长标题多少字符 | `SELECT MAX(LENGTH(title)) FROM tasks;` | **100** |
| 8 | 一共有多少种标题 | `SELECT COUNT(DISTINCT title) FROM tasks;` | **25** |

👉 **截图**（把 SQL 和结果表格一起截进去），命名 `03-数据质量核查SQL结果.png`

## 第 5 章 · 和接口测试交叉验证（三个实验）

### 5.1 【缺陷 D3】用数据库证明"数据真的被删掉了"（最值钱）

之前我们用 Postman / Fiddler 证明"没有 token 也能删除成功（204）"，
但那还只是**接口返回码**层面的说法。**再加一层数据库证据，就无懈可击了。**

**步骤**

1. Navicat 查询窗口执行 `SELECT COUNT(*) FROM tasks;`，**记下这个数字**，记为 `N`
2. 用 Postman（或 PowerShell）**不带任何 token** 发一次删除：

```
DELETE http://127.0.0.1:8000/tasks/<随便一个真实 id>
```

3. 回到 Navicat，**按 Ctrl+R 重新运行同一条 SQL**
4. 数字变成 **`N - 1`**

**结论**：未登录的请求不仅"返回了成功码"，还**真的把数据从数据库里删掉了**。

👉 **截图**：删除前的数字 + 删除后的数字，命名 `04-删除前.png`、`05-删除后.png`

### 5.2 【缺陷 D1】接口的长度限制，在数据库里也能看到

1. 用 Postman 发 `POST /tasks`，title 填 **101 个字符** → 收到 **422**
2. 回 Navicat 执行 `SELECT COUNT(*) FROM tasks WHERE LENGTH(title) > 100;`
3. 结果**仍然是 0**

**结论**：限制是在**接口层**做的，数据库里根本不可能出现超长数据。
但接口文档里**完全没有写这条限制** → **契约与实现不一致**（缺陷 D1）。

### 5.3 脏数据：数据库和自动化测试同时抓到了同一个问题

第 4 章第 2 条查出来 **2 条空标题**记录。

回想一下：之前跑数据库一致性测试时，有一条用例是**预期失败（xfail）**的，原因写着：

> "已知问题：空标题 / 纯空格未被校验，会作为脏数据落库"

**同一个问题，测试代码里抓到了，数据库里也看到了** —— 两边互相印证。
这句话面试时可以直接讲：

> "这个问题我先在自动化用例里以 xfail 标记固定下来，
> 又到数据库里确认脏数据确实落库了，所以它不是猜测，是双份证据。"

## 第 8 章 · 常见问题

| 现象 | 原因 | 怎么办 |
|------|------|-------|
| 测试连接失败 | 文件路径选错 | 重新点 `…` 选 `D:\qa-projects\00-demo-api\tasks.db` |
| 看不到 `tasks` 表 | 服务没启动过 / 连到了别的文件 | 先启动 demo-api；确认连的是 `main` 下的表 |
| 中文显示乱码 | 编码设置 | 连接属性 → 高级 → 编码选 `UTF-8`（或 `936`） |
| 数据一直在变 | 服务在跑、还有别的测试在写 | 正常，核查时注意记下时间点 |
| 试用版到期 | 14 天限制 | 换 **SQLiteStudio**（免费免安装），SQL 完全一样 |
| 结果只显示 1000 行 | 默认分页 | 不影响 `COUNT(*)` 这类统计 |
