# 数据库核查说明（Navicat）

## 1. 核查目标

接口测试只能证明"**接口返回了什么**"，**数据库才能证明"数据真的变成了那个样子"**。
本次核查做两件事：

1. **数据质量核查**：直接用 SQL 检查数据库里是否存在脏数据、越界值、重复值；
2. **接口与数据库交叉验证**：为接口测试发现的缺陷补上**数据层证据**。

---

| 项目 | 内容 |
|------|------|
| 数据库类型 | SQLite 3（单文件） |
| 数据库文件 | `D:\qa-projects\00-demo-api\tasks.db` |

| 表结构 | `CREATE TABLE tasks (id TEXT PRIMARY KEY, title TEXT NOT NULL, done INTEGER DEFAULT 0)` |
| 连接方式 | Navicat → 新建连接 → SQLite → 指向上述文件 |

## 3. 数据质量核查 SQL 与结果

执行方式：Navicat → 查询 → 新建查询 → 粘贴 SQL → **Ctrl+R** 运行。

| # | 检查项 | SQL | 实测结果 | 判定 |
|---|-------|-----|---------|------|
| 1 | 总行数 | `SELECT COUNT(*) FROM tasks;` | **1830** | 基线 |
| 2 | 空标题 / 纯空格标题 | `SELECT COUNT(*) FROM tasks WHERE title IS NULL OR TRIM(title) = '';` | **2** | ⚠️ **存在脏数据** |
| 3 | 超长标题（>100 字符） | `SELECT COUNT(*) FROM tasks WHERE LENGTH(title) > 100;` | **0** | ✅ 无越界数据 |
| 4 | `done` 取值异常 | `SELECT COUNT(*) FROM tasks WHERE done NOT IN (0,1);` | **0** | ✅ 取值合法 |
| 5 | 主键重复 | `SELECT id, COUNT(*) c FROM tasks GROUP BY id HAVING COUNT(*) > 1;` | **0 行** | ✅ 唯一性正常 |
| 6 | `done` 分布 | `SELECT done, COUNT(*) FROM tasks GROUP BY done;` | `0 → 1828`、`1 → 2` | 状态分布合理 |
| 7 | 最长标题长度 | `SELECT MAX(LENGTH(title)) FROM tasks;` | **100** | 正好卡在接口限制的边界 |
| 8 | 不同标题数量 | `SELECT COUNT(DISTINCT title) FROM tasks;` | **25** | 数据多样性 |

## 4. 三个关键实验

### 4.1 实验一：为「未授权删除」补数据层证据（缺陷 D3）

**背景**：接口层发现 `DELETE /tasks/{id}` 不校验身份，未授权请求返回 **204**。
但 204 只说明"返回码不对"，**不能证明数据真的被删了**（可能只是返回码写错）。

**步骤**

1. Navicat 执行 `SELECT COUNT(*) FROM tasks;` → 记下行数 **N**；
2. 用 Postman 发送**不带 Authorization** 的 `DELETE /tasks/{id}`（返回 204）；
3. 回到 Navicat，**Ctrl+R 重新执行同一条 SQL**；
4. 行数变为 **N - 1**。

**结论**：未登录的请求不仅"返回了成功码"，还**真的把数据从数据库里删掉了**。
据此把缺陷严重度从"错误码不规范"升级为「**高危越权 + 数据破坏**」。

> 这一条是**双工具 + 数据层**三方证据的一部分：
> Postman（请求层）＋ Fiddler（传输层，抓包确认请求头里确实没有 Authorization）＋ Navicat（数据层）。

### 4.2 实验二：接口的长度限制在数据库里可验证（缺陷 D1）

**背景**：接口文档没有声明 `title` 长度限制，但发 101 个字符会被拒绝（422）。

**步骤**

1. 用 Postman 发 `POST /tasks`，`title` = 101 个字符 → 收到 **422**；
2. Navicat 执行 `SELECT COUNT(*) FROM tasks WHERE LENGTH(title) > 100;` → **仍然是 0**。

**结论**：限制是在**接口层**实施的，数据库里不可能出现超长数据；
同时最长标题恰好 **100** 字符，说明**边界正好卡在 100**。
但这条限制在接口文档里**完全没写** → 属于**契约与实现不一致**。

### 4.3 实验三：脏数据与自动化测试的 `xfail` 互相印证

第 3 章第 2 条查出 **2 条空标题记录**。

而在项目一的 pytest 数据库一致性用例中，有一条被标记为**预期失败（xfail）**：

```text
test_empty_title_should_not_be_persisted
已知问题：空标题 / 纯空格未被校验，会作为脏数据落库
```

**同一个问题，测试代码里抓到了，数据库里也看到了** —— 两边独立印证。
这比"我说它有 bug"要有力得多。

> 💡 面试话术："这个问题我先在自动化用例里以 xfail 固定下来，
> 又到数据库里确认脏数据确实落库了 —— **它不是猜测，是双份证据**。"

---

## 5. 结论

1. 数据整体质量良好：**主键唯一、取值合法、无超长数据**；
2. 存在 **2 条空标题脏数据**，对应接口缺少入参内容校验（与 `xfail` 用例一致）；
3. **越权删除是真的删掉了数据**（行数 N → N-1），缺陷严重度成立；
4. 「最长标题 = 100」与「101 字符被拒」共同证明了**未文档化的长度边界**。

---

## 6. 局限

| 局限 | 说明 |
|------|------|
| 单机 SQLite | 没有并发连接与锁等待的真实场景，不能代表生产数据库行为 |
| 只做只读核查 | 未验证"用图形工具改数据"这类操作（避免污染环境） |
| 数据量小（1830 行） | 索引与查询计划的表现不代表大数据量场景 |
| 快照随时在变 | 服务仍在运行，行数会随测试数据增长而变化（核查时需记录时间点） |
