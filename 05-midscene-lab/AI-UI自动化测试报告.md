# AI UI 自动化测试报告（Midscene + Playwright）

> 被测对象：TodoMVC（https://demo.playwright.dev/todomvc）
> 测试工具：Midscene 1.13.0 + Playwright + Node.js v22.23.2
> 测试时间：2026-09-22
> 用例规模：7 条 × 5 轮 = 35 次执行

---

## 1. 测试目标

1. 验证"视觉大模型驱动 UI 自动化"的可行性（不写 CSS 选择器，用自然语言操作）；
2. 量化其**稳定性**，与"传统选择器脚本易碎"的痛点做对比；
3. 建立"AI 调用成本"的量化基线；
4. 验证 AI 是否会被页面文案劫持（Prompt 注入防护）。

---

## 2. 测试策略：混合模式（本次最重要的方法论结论）

初期版本把**所有操作**都交给 AI（`aiAct`），结果第一条用例就失败（详见第 5 节）。
分析后改为**分层策略**：

| 操作类型 | 交给谁 | 理由 |
|----------|--------|------|
| 填输入框、按回车、数元素个数 | **Playwright 确定性 API** | 有稳定定位方式，AI 做会"漏动作" |
| 定位"勾选框""hover 才出现的删除按钮" | **Midscene `aiAct`** | 无稳定选择器，需要"看" |
| 语义断言（内容对不对） | **Midscene `aiAssert`** | 传统断言无法表达 |
| 状态断言（是否勾选、条数对不对） | **Playwright `expect(locator)`** | 确定性、快、免费 |

**核心实现**（`tests/02_todo_full.spec.ts`）：

```ts
/** 用确定性方法添加待办，并等它真的进列表（防止"假成功"） */
async function addTodo(page: Page, text: string) {
  const before = await items(page).count();
  await newTodo(page).fill(text);
  await newTodo(page).press('Enter');
  await expect(items(page)).toHaveCount(before + 1, { timeout: 10_000 });  // ← 关键卡点
}
```

最后那句 `toHaveCount` 是防"假成功"的关键：**每一步操作都必须被确定性断言确认**，才允许继续。

## 5. 优化前的两个真实缺陷（失败归因）

### 缺陷 1：AI 的多步规划会"漏动作"

**现象**：优化前的用例 `aiAct('在输入框输入 "任务A" 并回车')` 连续执行三次，
最终列表里只有 1 条待办，输入框里残留着"任务C"。

**证据**（从 Midscene 执行报告中提取的动作序列）：

| 执行 | AI 规划出的动作 | 结果 |
|------|----------------|------|
| 第 1 次（任务A） | 点击输入框 → 输入文本 → **按回车** | ✅ 成功 |
| 第 3 次（任务C） | 点击输入框 → 输入文本 | ❌ **回车动作缺失** |

**归因类别**：模型波动（同一条指令，多次规划出的动作数不一致）
**修复**：确定性操作交回 Playwright（`fill` + `press`），AI 不再负责这类动作。

### 缺陷 2：AI 断言会"误判"，掩盖真实失败

**现象**：`aiAssert('待办列表中存在待办：任务B')` **通过了**，
但事后的页面快照显示：任务B 其实还躺在**输入框**里，从未进入列表。

**证据**（失败时的 Playwright 页面快照）：

```yaml
- textbox "What needs to be done?" [active]: 任务B   ← 文字在输入框里
- list:
    - listitem: 任务A                                  ← 列表里只有任务A
```

**归因类别**：模型波动（AI 把"输入框里的文字"误判为"列表项"）
**影响**：错误被前面几条断言掩盖，直到最后一条断言才暴露 → **排查成本成倍增加**
**修复**：状态类断言改用 `expect(locator).toHaveCount()`。

> 📌 **这两条都是"AI UI 自动化"特有的可靠性问题**，传统选择器脚本不会遇到（因为没有"规划"和"视觉判断"这一步）。
> 它们的实践意义是：**AI 的输出必须被确定性断言兜底**。

## 7. 成本统计

| 指标 | 数值 | 说明 |
|------|------|------|
| 单轮高层 AI 调用 | 5 次 | 2 次 `aiAct` + 3 次 `aiAssert` |
| 5 轮高层 AI 调用 | 25 次 | — |
| 实际模型请求 | 约 15~25 次/轮 | `aiAct` 内部还包含"规划→定位→执行"多轮交互 |
| 单轮耗时 | 60.3 秒 | 其中 AI 相关用例占约 55 秒 |
| 费用 | 以百炼控制台用量统计为准 | 视觉模型的输入含截图，token 消耗高于纯文本 |

**成本结论**：AI 用例的耗时与费用主要集中在**视觉模型调用**上。
把确定性操作从 AI 手里拿回来，是**降本增效最直接的手段**（本次单条用例 AI 调用从 7 次降到 1 次）。

## 8. 结论与局限

### 8.1 结论

1. **AI UI 自动化可行，但有明确边界**：适合"无稳定选择器 / 需要视觉判断 / 语义断言"的场景；
   不适合"填表单、点有 id 的按钮"这类确定性操作。
2. **稳定性来自架构设计，而不是"AI 本身很稳"**：本次 flaky 率 0.0% 是
   "AI 只负责它擅长的部分 + 确定性断言兜底"的结果；
3. **AI 的两个特有风险已被实测证实**：规划漏动作、断言误判，
   两者都会导致"失败被掩盖"，必须用确定性断言把关；
4. **成本可观可控**：通过缩小 AI 的使用范围，单条用例 AI 调用从 7 次降至 1 次。

### 8.2 局限

1. 被测站点是 TodoMVC **公开练习站点**，页面结构简单，**不代表复杂业务系统的真实难度**；
2. 仅 7 条用例、5 轮，**样本量偏小**，0.0% flaky 率的置信度有限；
3. 未做**多模型对比**（不同视觉模型的稳定性与成本差异）；
4. 未在 **CI（无头环境）** 中验证，无头模式下截图可能异常（社区已知问题）；
5. 优化前后的对比基线不完整（优化前仅 1 次执行记录）。

### 8.3 后续计划

1. 用旧版本跑 5 轮，补齐"优化前 flaky 率"基线；
2. 增加模型对比实验（豆包 / Qwen-VL / GLM），比较稳定性与单次成本；
3. 接入 GitHub Actions（xvfb + headless），验证 CI 中的表现；
4. 把用例扩展到真实业务系统（登录、下单、表单校验）。
